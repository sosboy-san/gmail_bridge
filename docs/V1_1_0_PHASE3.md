# v1.1.0 Phase 3 実装記録（開発中）

Phase 3では、QNAP / Container Stationの初回自動起動に対応する常駐サービスの安全待機と復帰を実装しました。正式版の公開はまだ行いません。

## 起動と待機

毎周期、次のローカル確認を行ってからrunを起動します。

1. config.iniを再読込・検証。
2. init/run/cleanup/statusと同じ共通ロックを取得。
3. 既存DBを検証・必要ならPhase 2の方式で移行。
4. 対象mailboxの初期化完了記録を確認。
5. OAuthファイルのJSON項目・読み書き可能性を確認。
6. DB接続・共通ロックを解放してrunを起動。

待機時はIMAP/Gmail/Drive/ntfyの処理を開始しません。DBがない場合でも、常駐サービス自身はDBを作成しません。共通ロック取得でdataディレクトリとlockファイルが作成される場合があります。

| 状態 | ログ | 復帰条件 |
| --- | --- | --- |
| DBなし・mailbox未初期化 | `[WAITING_FOR_INIT]` | 利用者による明示的なinit完了 |
| 別コマンドが実行中 | `[WAITING_FOR_LOCK]` | 共通ロック解放 |
| INI不正・必須設定不足・OAuthファイル不正 | `[CONFIG_ERROR]` | ファイル／設定の修正 |
| DB破損・未知の構造／スキーマ | `[DB_ERROR]` | 利用者による適切な修復／復元 |
| backup／migration失敗 | `[DB_MIGRATION_ERROR]` | 失敗原因の解消 |
| ローカルI/O等の失敗 | `[SERVICE_ERROR]` | ファイル／権限等の修正 |
| 起動条件を満たした | `[CONFIG_OK]` | 処理周期を開始 |

次の確認は60秒待機後です。待機中にConsoleからinitを実行でき、完了すれば再起動なしで次周期に通常運用へ移ります。同じ待機ログは状態／説明が変化するまで繰り返しません。自動initは追加しません。

DB破損時は、空DB作成・initへの切替・バックアップからの自動復元を行いません。修復／復元は利用者の明示的な操作です。

## 設定検証

新しい通知設定の型・値を検証する基盤を追加しました。

- include_sender / include_subjectのboolean。
- sender_filter_modeはoff / allowlist / blocklist / combined。
- ttl_minutesは0以上の整数。未指定／0は従来互換の無期限。
- 通知が有効な場合、provider / topic / server_url / tokenの形式も検証。
- 通知が無効、またはフィルタがoffなら、送信元リストファイルは読みません。
- 通知が有効かつフィルタ有効の場合だけ、別INIのセクション・キー・アドレス・ドメインを検証。
- 明確に不正な設定をoff等へfallbackしません。

設定値・パスの制限はBRIDGE_CONFIG_DIRを使用する場合にも適用します。新方式のファイル欠落時に旧パスを探しません。

OAuth確認はローカルのJSONと権限確認だけです。認証・token refresh・リモートAPIへの通信は行いません。CLIのrun開始時にもOAuthファイルを再確認します。OAuth有効性や通信先の到達性まで保証するものではありません。

**このPhaseでは通知設定の検証だけを追加しています。送信元フィルタによる通知対象の判定、送信元・件名の表示、TTLによる期限切れはPhase 4の実装範囲です。**

## 処理周期と終了

runが非ゼロで終了した周期はcleanupを開始しません。cleanup開始前にもローカル確認をやり直し、設定変更・init競合等があれば開始を延期します。cleanupが成功した場合だけ当日の完了記録を保存します。

起動済みの子コマンドは自身の設定スナップショットで処理を完了します。途中で強制停止せず、次のコマンド開始時に設定を再確認します。通知送信直前の設定再判定はPhase 4で実装します。

SIGTERM / SIGINTでは稼働中の子処理が終了した後に常駐サービスを停止します。待機中はEvent経由で停止できます。
